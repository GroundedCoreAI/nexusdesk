# groundedcoreai-requirement-lifecycle

nexusdesk 的需求全流程文档驱动工作方式。核心原则：**文档先行、逐阶段对照执行、每阶段结束留下结论性文档；验收精简不等于降低技术门槛**。

标准范本：`docs/requirement/agent-execution-platform-v2/phase-* /05-acceptance-plan.md`（本仓库已统一为"最小核心团队"验收标准；旧版多角色/业务指标/UAT 格式仅作历史参考，不得覆盖本 skill 的默认规则）。

## 文档套件结构

每个需求主题在 `docs/requirement/<topic>/` 下组织；主题内按阶段建 `phase-N-<slug>/` 目录
（单阶段需求也建 `phase-1-<slug>/`，保持结构一致）。主题根目录放一份 `README.md` 作索引
（背景、总体原则、阶段路线图表、明确不做的边界、Review 指引）。

每个阶段目录下的标准套件（编号即顺序，前缀不得改动）：

| 文件 | 产物阶段 | 内容 | 何时写 |
|---|---|---|---|
| `01-business-goals.md` | 需求分析 | 要解决的问题、业务目标（G1..）、必要的成功指标（基线/目标）、范围边界、风险约束 | 动手前 |
| `02-requirements.md` | 需求分析 | 用户故事（US-n）、功能需求（FR-n）、非功能需求、验收标准（AC-n） | 动手前 |
| `03-technical-design.md` | 需求分析 | 改动总览、数据模型/迁移、核心流程、配置项、测试方案简表、上线与回滚 | 动手前 |
| `04-test-plan.md` | 需求分析 | 测试范围与原则、环境、UT/IT/CM 用例表（含溯源列）、回归范围、缺陷分级与出口准则 | 动手前 |
| `05-acceptance-plan.md` | 需求分析 | 验收范围与责任（最小核心团队）、环境前置、AC 逐条验收（A1..）、少量关键人工检查、安全/数据硬门槛（C-n）、通过标准与单一验收记录 | 动手前 |
| `08-implementation-breakdown.md` | 设计评审后（可选，大型阶段建议） | 任务拆解表（T-n：文件/依赖/溯源）、文档与现实不一致清单及裁定（R-n） | 开发启动时 |
| `06-test-report.md` | 测试结束 | 逐条用例执行结果（测试位置/环境/结果/证据）、缺陷记录（D-n）、残留风险（R-n）、CI 证据、输出快照附录 | 测试完成后 |
| `07-acceptance-report.md` | 验收结束 | AC 与适用硬门槛判定及证据、必要的指标结果、遗留清单（L-n）、结论与单一验收记录 | 验收完成后 |

模板骨架在 `assets/templates/` 下，写文档时**先读对应模板再写**，保持章节与表格结构一致。

## 最小核心团队验收（唯一默认规则）

本项目处于起步阶段、团队规模小，验收组织精简到**一名验收负责人即可完成**，但不以降低技术门槛为代价。所有阶段的 `05` / `07` 一律遵守：

1. **单一责任主体**：默认只设"验收负责人"一名，可自行执行并作结论；确需协助时设"执行人"，允许与验收负责人为同一人。不生成产品/QA/研发/Adapter/安全/SRE/财务/业务代表的职责表，不设多角色签字表，不虚构独立评审。
2. **不设独立 UAT 轮次**：把需要人工判断的体验或业务问题转成最多 3~5 条"关键人工检查"，映射到 A/AC。开发者自验只代表符合已写需求，不冒称真实用户或独立业务验收。
3. **不生成业务指标大表**：能由 UT/IT/CM 或 A 场景证明的正确性直接复用证据。只有确实会改变放行决策的性能、容量指标才保留，原则上 1~3 项，并入 A/C 的判据、样本与测量方法；未测量写 `pending_env` / `not_measured`，不得编基线或写成通过。
4. **硬门槛只按阶段风险裁剪**：只保留与阶段风险有关的租户隔离、Secret、数据完整性、迁移、终态/副作用、回滚要求；优先引用自动化断言、CI、数据库/OS/网络证据，不为 C 项重复手工跑整套测试。
5. **单一验收记录替代签字**：记录验收负责人、执行人、日期、目标 SHA、结论、证据链接及遗留项 owner/期限。P2/P3 遗留由验收负责人在该记录中确认，不再要求多角色签字。
6. **"阶段验收通过"与"高风险能力启用"严格分离**（关键）：阶段验收只判断代码是否正确、默认关闭状态下是否安全、既有路径是否无回归；**开放不可信多租户代码执行、生产 Codex 路由等高风险能力，必须另有独立安全与运维批准记录，绑定目标 SHA、租户范围、批次、证据与撤销条件**。缺少人员或真实环境时相应开关保持 `false`，不得靠删除流程或签字要求放行。阶段通过绝不自动构成启用授权。
7. **证据复用、如实记录**：A/C 优先引用 `06` / CI / DB / OS 原始证据；未跑、skip、环境缺失、`not_measured` 如实写明，禁止写成通过或把待办改标为已完成。
8. **修订旧文档保持溯源一致**：删除或降级已有指标、审批或验收承诺时，同步检查并修订 `01/02/03/04/05` 的 G/US/FR/NFR/AC、测试与放行门禁引用；中英文一起改。不得只删 `05` 而留下互相矛盾的上游承诺。

## 工作流程

### 阶段一：需求分析（文档先行）

接到需求后，先不写代码：

1. 确定主题目录：已有主题则在其下新建 `phase-N-<slug>/`；新主题则建
   `docs/requirement/<topic>/` 并写主题 `README.md` 索引。
2. 按模板依次产出 `01`~`05` 五份规划文档。写作要求：
   - **一切编号可溯源**：业务目标 G-n、用户故事 US-n、功能需求 FR-n、验收标准 AC-n，
     后续测试用例、验收步骤必须用"溯源"列指回这些编号；
   - 技术设计必须落到**具体文件路径与迁移号**，先核查现状代码再写（不写与代码现实矛盾的方案）；
   - 测试方案的用例编号规则：`P<N>-UT-xx`（单元）、`P<N>-IT-xx`（集成）、`P<N>-CM-xx`（通用核对项），
     N 为阶段号；每条用例带"预期"与"溯源"两列；
   - 验收方案的 A1.. 与 AC 一一对应，每个场景写明通过判据；C 项仅列适用硬门槛并复用测试证据；
   - 默认执行"最小核心团队验收"规则，不自行扩写多角色 UAT、业务指标大表和签字表；
   - 明确"范围不包含"清单，防止阶段蔓延。
3. 五份文档完成后向用户汇报要点，**等用户确认（或要求直接继续）后再进入开发**。

### 阶段二：设计/开发/调试（对照执行）

1. 大型阶段先补 `08-implementation-breakdown.md`：把 03 拆成任务表（T-n：涉及文件、依赖顺序、溯源），
   并设"文档与现实不一致清单及裁定"（R-n）一节——开发中每发现文档与代码现实冲突，先登记裁定再动手，
   裁定结果回填相关文档。
2. 开发按 T-n 依赖顺序执行；每完成一个任务对照 02 的 FR 与 03 的设计自查。
3. 调试中发现设计需要变更时，**先改 03（注明修订日期与原因），再改代码**——文档与代码不同步是本项目
   测试报告/验收报告的主要缺陷来源。
4. 提交遵循 `groundedcoreai-commit-standard`；分支/PR 流程遵循 `groundedcoreai-dev-workflow`。

### 阶段三：测试（对照 04 执行 → 产出 06）

1. 逐条执行 `04-test-plan.md` 的 UT/IT/CM 用例，**不允许只做"大体跑了下"**——06 报告要求每条用例
   有独立行：测试位置（文件::用例）、执行环境、结果、证据。
2. 出口准则未达成（P0/P1 未关闭、回归非全绿、开关兜底 diff 非零）不得进入验收。
3. 完成即写 `06-test-report.md`：执行总览、逐条结果、缺陷记录（D-n：级别/发现环节/修复提交/回归）、
   残留风险（R-n）、CI 证据（run 链接）、本地执行输出快照附录。如实记录 skip 与环境约束，禁止粉饰。

### 阶段四：验收（对照 05 执行 → 产出 07）

1. 验收负责人逐条核对 05 的 A1.. 场景与适用 C-n 硬门槛；自动化测试已覆盖的直接引用 06/CI 证据，只实际执行少量无法自动化的人工检查。
2. 本环境无法执行的项标 `pending_env`，写明所需环境与补测责任；额外指标未测量标 `not_measured` 或 `pending_env`。不得跳过不写、写成通过，也不得把"高风险能力启用"的独立审批缺失误记为阶段不通过——它是单独的放行前置。
3. 完成即写 `07-acceptance-report.md`：逐条判定与证据、遗留清单（L-n：级别/owner/期限）、结论（通过 / 有条件通过 / 不通过）与单一验收记录。允许验收负责人和执行人为同一人，不得虚构独立评审。放行高风险能力时另附独立审批记录链接。

## 通用规则

- **语言**：`docs/` 下同一份文档如保留中英对照，须在同一提交内同步更新；最小完整套件可只写英文版。
- **状态头**：每份文档开头用引用块标注：状态、创建日期、依据（上游文档及编号）；修订时追加"修订：<日期>"行并保留历史。
- **如实记录**：测试/验收报告的价值在于可信。skip、环境限制、未能核验的计数都要写明边界，
  不许把"没跑"写成"通过"。
- **后端/前端/脚本改动**仍须遵守对应的 `groundedcoreai-python-backend-standards` /
  `groundedcoreai-typescript-frontend-standards` / `groundedcoreai-shell-infra-standards`，
  本 skill 只规定文档流程，不替代编码规范。
- 完成前自检：后端 `cd backend && uv run ruff check src tests && uv run pytest`；
  前端 `cd frontend && npm run typecheck && npm run check:i18n && npm run build`。
