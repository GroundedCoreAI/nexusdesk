## 0. 结论摘要

人工工作台不是第二套客服系统，也不是脱离业务场景的通用聊天窗口。它是服务场景的人工承接端：

```text
服务场景识别
  → 业务对象绑定
  → 业务事实投影
  → 用户决策与待确认动作
  → 自动处理或转人工
  → 人工工作台继承完整业务上下文
```

工作台必须让坐席在不重新询问客户的情况下回答以下问题：

1. 客户是谁，从哪个渠道进入？
2. 客户正在处理哪个业务场景？
3. 客户选中的业务对象是什么？
4. 系统已经拿到哪些业务事实？
5. 客户做过哪些选择或确认？
6. 为什么转人工，自动服务做到哪一步？
7. 当前有哪些待确认动作或未完成运行？

V1 不把工作台做成全功能工单系统。工单能力继续由现有服务工单模块承载，人工工作台聚焦实时队列、接管、上下文、处理与恢复自动服务。

## 1. 产品边界

### 1.1 工作台负责

- 查看等待接管和处理中的交接队列。
- 按状态、处理人和关键词筛选。
- 查看交接摘要、客户信息、会话消息和业务上下文。
- 接管会话并将会话切换为人工模式。
- 处理结束后恢复 Agent，或直接关闭会话。
- 显示权限不足、加载失败、空队列和并发冲突。
- 保留会话、交接和操作审计。

### 1.2 工作台不负责

- 不复制 Agent 配置，不在这里编辑 Prompt、模型或工具。
- 不复制服务场景配置，不在这里修改对象、事实或决策。
- 不新增行业专属客服页面。
- 不把工单状态流转塞进人工交接状态。
- 不以“审核工作”替代业务审批；审批仍跟业务对象、场景或 Agent 绑定。
- 不允许人工跨租户或跨业务范围查看会话。

### 1.3 三个概念必须分开

| 概念 | 含义 | 主要状态 |
|---|---|---|
| 会话模式 | 当前由谁承接客户 | `bot` / `waiting` / `human` / `closed` |
| 交接状态 | 人工协同任务的状态 | `waiting` / `active` / `resolved` |
| 业务处理状态 | 客户问题本身处理到哪一步 | 待确认 / 处理中 / 成功 / 失败 / 结果未知 / 转人工 |

三者不能合并成一个状态字段。客户问题已成功但会话仍需跟进、交接已结束但业务动作仍在处理中，都是合法场景。

## 2. 用户与权限

| 角色 | 可以查看队列 | 可以查看上下文 | 可以接管 | 可以恢复/关闭 | 可以分配他人 |
|---|---:|---:|---:|---:|---:|
| 只读成员 | 是 | 是 | 否 | 否 | 否 |
| 操作员 | 是 | 是 | 是，仅本人 | 是，仅本人处理的交接 | 否 |
| 管理员 | 是 | 是 | 是 | 是 | 是 |

权限仍由现有访问控制和业务范围约束。前端隐藏按钮只是体验层，后端必须继续执行租户、业务范围、处理人和 revision 校验。

## 3. 核心工作流

### 3.1 自动服务申请人工

```text
客户消息
  → 路由识别转人工
  → 会话模式 waiting
  → 创建交接记录
  → 取消排队中的自动运行
  → 通知工作台
```

交接记录至少包含：

- 交接编号和会话编号。
- 转人工原因。
- 转人工摘要。
- 创建时间和更新时间。
- 当前状态与处理人。
- 客户、业务范围和工作区标识。

### 3.2 坐席接管

```text
选择等待中的交接
  → 查看摘要和上下文
  → 接管
  → 交接 active
  → 会话 human
  → 记录处理人
```

接管必须携带当前 revision。若其他坐席已接管，返回 revision 冲突，不覆盖对方操作。

### 3.3 结束并恢复 Agent

```text
人工处理完成
  → 结束交接
  → 交接 resolved
  → 会话恢复 bot
  → 写入系统消息
  → 保留摘要、消息和审计
```

### 3.4 关闭会话

```text
人工确认无需继续
  → 结束交接
  → 交接 resolved
  → 会话 closed
  → 后续消息按关闭会话规则处理
```

“恢复 Agent”和“关闭会话”是两个明确动作，不能都显示为“完成”。

## 4. 上下文继承

### 4.1 上下文分层

| 层级 | 内容 | 用途 |
|---|---|---|
| 客户层 | 客户标识、来源渠道、外部会话标识 | 确认服务对象与渠道 |
| 会话层 | 会话模式、最近消息、摘要、处理人 | 理解当前沟通状态 |
| 场景层 | 服务应用、服务场景、场景版本 | 理解客户正在办理什么 |
| 对象层 | 主业务对象类型、对象引用和安全展示值 | 避免坐席重新询问订单/账号等 |
| 事实层 | 已投影的业务事实、脱敏信息 | 快速判断问题 |
| 决策层 | 客户已选决策、确认结果、可纠正项 | 判断是否已经授权 |
| 动作层 | 待确认动作、动作状态和结果 | 继续办理或核查结果 |
| 执行层 | 最近运行、失败原因、路由决策痕迹 | 解释为什么转人工 |

### 4.2 上下文展示原则

1. 只展示坐席完成服务所需的信息。
2. 敏感字段按原业务权限脱敏，不因为坐席身份自动放开。
3. 不展示 Provider、工具标识、Prompt、内部规则键等实现术语。
4. 对象引用使用稳定标识，不复制完整业务快照。
5. 事实必须带业务名称和值；缺失时显示“暂无数据”，不伪造默认值。
6. 用户决策必须能区分已选择、已确认、待确认和已取消。
7. 转人工原因和自动处理轨迹必须保留原始依据，便于追责。

### 4.3 当前实现与缺口

当前工作台已通过会话详情展示客户、业务范围、最近消息、待确认动作和最近运行。

H2 第一增量已落地（见 [人工工作台业务上下文](./handoff-context-v1.md)）：

- 场景轨迹可用 `conversation_id` 绑定真实会话。
- `GET /api/v1/handoffs/{id}/context` 返回应用、场景、对象、事实、决策、动作、运行、路由决策和轨迹。
- 权限裁剪与脱敏在服务端完成，客户标识仅以 `has_customer` 形式出现。
- 工作台新增“自动服务”区块展示场景、对象、事实与用户决策。

仍缺少：

- 运行时尚未真正写场景轨迹，目前只有模拟入口会写。
- 场景版本尚未在会话创建时固化。
- 事实的 `refresh` 策略没有在人工视角生效，当前只返回轨迹快照。

下一增量的落点不是新增工作台专属业务表，而是在路由把会话交给场景执行时落一条 `simulation=false` 的通用轨迹，再复用现有聚合器：

```text
runtime_conversations
  + routing decisions
  + service scenario traces
  + pending actions
  + recent runs
  → HandoffContext
```

聚合器只做读取、权限裁剪和业务化投影，不按行业分支。

## 5. 队列设计

### 5.1 默认排序

1. 等待接管优先于处理中。
2. 同状态内按等待时长从长到短。
3. 高风险、结果未知和即将超时的交接可提升优先级。
4. 已解决记录默认不进入实时队列，可在历史筛选中查看。

### 5.2 筛选

- 全部实时交接。
- 等待接管。
- 我的处理中。
- 可按交接编号、外部会话标识和转人工原因搜索。

V1 不提供任意条件组合筛选，避免在队列规模未验证前过度设计。

### 5.3 列表卡片

- 交接编号或外部会话标识。
- 状态。
- 转人工原因。
- 处理人。
- 等待或处理时长。
- 摘要首行。
- 可选的风险、结果未知、超时和高优先级标记。

### 5.4 详情区

- 交接摘要。
- 客户和渠道。
- 场景与业务对象。
- 业务事实。
- 用户决策。
- 待确认动作。
- 最近运行和路由原因。
- 最近消息。
- 接管、恢复 Agent、关闭会话。

## 6. 异常与恢复

| 场景 | 产品行为 |
|---|---|
| 队列加载失败 | 展示错误原因和重新加载，不清空已有队列 |
| 没有交接 | 展示空状态和刷新动作 |
| 会话详情加载失败 | 交接详情仍可用，单独提供上下文重试 |
| 两人同时接管 | 后操作者收到冲突提示并刷新 |
| 当前用户非处理人 | 禁止恢复或关闭，并说明原因 |
| 交接已结束 | 隐藏实时处理动作，保留历史详情 |
| 客户消息到达但会话已关闭 | 按现有会话关闭策略处理，不重新激活旧交接 |
| 自动处理结果未知 | 明确标记“结果待确认”，禁止显示成功 |

## 7. 数据与接口边界

### 7.1 V1 复用接口

```text
GET  /api/v1/handoffs
POST /api/v1/handoffs/{id}/transition
GET  /api/v1/conversations/{id}
GET  /api/v1/me
```

### 7.2 后续建议接口

```text
GET /api/v1/handoffs/{id}/context
```

返回聚合后的：

- handoff。
- conversation。
- application / scenario / version。
- object。
- facts。
- decisions。
- pending actions。
- recent runs。
- routing decisions。
- scenario traces。

接口应在服务端完成权限裁剪和敏感字段脱敏，前端不自行拼接多个内部接口来推断业务事实。

## 8. 验收标准

### 8.1 功能

- 只读角色能查看队列与上下文，但不能操作。
- 操作员能接管等待中的交接，并只能结束自己处理的交接。
- 管理员能分配、接管、恢复和关闭。
- revision 冲突不会覆盖其他坐席操作。
- 接管后会话进入人工模式，恢复后回到自动模式，关闭后不可继续自动回复。
- 空队列、加载失败、权限不足和会话详情失败均有明确状态。

### 8.2 上下文

- 坐席无需客户重复提供订单号、账号等对象标识。
- 坐席能看到转人工前已投影的业务事实。
- 坐席能看到客户已做决策和待确认动作。
- 坐席能看到转人工原因和自动处理轨迹。
- 敏感字段遵守原有权限和脱敏规则。

### 8.3 质量

- 工作台在桌面和窄屏均可用。
- 无控制台错误和页面异常。
- 关键操作有审计记录。
- 新增文案进入四语言词典。
- 与现有会话工作台、服务工单和 Agent 管理无回归。

## 9. 实施切片

### 切片 H1：实时队列与详情（当前）

- 队列、搜索、状态筛选。
- 接管、恢复、关闭。
- 会话消息、待确认动作和最近运行。
- 权限、空状态和错误状态。

### 切片 H2：业务上下文继承

- 轨迹绑定会话。
- 聚合场景、对象、事实、决策和路由原因。
- 服务端权限裁剪与脱敏。
- 工作台展示业务上下文。

### 切片 H3：协同与运营

- 分配组和坐席状态。
- 超时、优先级和升级规则。
- 快捷回复、内部备注和标签。
- 处理结果与客户满意度。

### 切片 H4：多行业复用

- 队列由场景配置映射，不由行业硬编码。
- 高风险办理场景可以指定专属队列。
- 行业包只提供队列建议和场景模板，不新增行业专属工作台。
- 通过内容社区、本地生活等第二个行业验证复用性。

---

## 10. 非目标

V1 明确不做：

- 全渠道 CTI 软电话。
- 复杂排班和工时管理。
- 独立知识库编辑器。
- 任意流程设计器。
- 以人工工作台替代工单中心。
- 为每个行业复制一套坐席页面。
- 用前端状态推断业务是否成功。
