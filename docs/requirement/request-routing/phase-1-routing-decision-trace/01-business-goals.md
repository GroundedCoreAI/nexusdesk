# Phase 1 · 路由决策可见 — 业务目标

> 阶段：Phase 1（MVP；含 FR-3、FR-4 两处**有意行为变更**）
> 预估工期：~1 周
> 依赖：无（不依赖 Phase 2-4）

## 要解决的问题

### 问题 1：入口判定不可见，线上问题无法归因

`business_capabilities/customer_service/service.py::send()` 用连续 `if` 决定一条消息的去向：

| 行号 | 分支 | 结果 |
|---|---|---|
| 129 | `mode == "closed"` | `DomainError("conversation_closed", 409)` |
| 131 | `message.strip() in {"转人工","人工客服"}` | 请求人工接管，不建 Run |
| 142 | `mode in {"human","waiting"}` | 只入库，不建 Run |
| 167 | 黑名单旗标命中且开关打开 | 请求人工接管，不建 Run |
| 其他 | — | 提交 Run，进入 ReAct |

五个分支**都不落任何结构化记录**。典型受损场景：客户投诉"我发了消息没人理"，排查时只能逐个翻应用日志、对照会话状态手工推断，无法回答"这条消息当时被判成了哪一类、依据哪一条"。同一个问题每次出现都要重新排查一遍。

### 问题 2：转人工识别只覆盖中文，且不可配置

第 131 行硬编码 `{"转人工", "人工客服"}`。平台已有 7 个渠道适配器与 4 种语言，海外用户在 Telegram / Discord / Slack 说 `human` 或 `客服` 不会被识别，消息会进入普通 ReAct 流程而不是转人工。裸 `agent` 因误触风险明确不纳入默认规则。同时该词表写在服务代码里，租户无法按业务习惯配置自己的人工请求表达。

### 问题 3：没有分流数据，后续档位无法证明收益

Phase 2 的 `direct` 档、Phase 3 的 `lightweight` 档都需要一个前提：**简单问题在真实流量中占比足够高**。当前没有任何按分支、按原因聚合的数据，无法回答"如果做确定性回答，能吃掉多少流量、省多少延迟"。在没有数据的情况下投入档位改造，存在投入产出不确定的风险。

## 业务目标

| 目标 | 说明 |
|---|---|
| G1：决策可查询 | 每条入站消息产生一条结构化决策记录（判成哪一类、依据什么、最终去向），可按会话、按租户、按原因查询与聚合 |
| G2：人工请求可配置且多语言 | 人工请求识别覆盖 zh-CN / zh-TW / en / hi 的**确定性关键词规则**（非意图识别）；确定性命中优先于模型；规则由客服能力自己持有，不进 Core |
| G3：产出分流基线数据 | 可统计各分支占比、各原因的分布，为 Phase 2/3 的收益测算提供依据 |

## 成功指标

| 指标 | 基线（现状） | 目标 |
|---|---|---|
| 决策覆盖率 | 0（无任何记录） | **数据库健康时** 100%，含两条 Reject 分支（`conversation_closed` / `model_not_configured`）；写入失败单独计数，不计入覆盖率 |
| 决策写入失败率 | — | < 0.1% 且可观测（CustomerService 内按 tenant 的进程内失败计数 + WARN 日志；跨副本失败率由日志聚合） |
| 兼容性 | — | **除 FR-3（规则扩展）与 FR-4（两条 409 改为返回结果）外**，其余分支在 HTTP 状态码与持久化副作用上与基线一致 |
| 人工请求规则命中 | 仅中文 2 个词硬编码 | 四语言用例集全部命中；句内表达（`I want to speak to a human`）明确记录为已知缺口 |
| 决策写入开销 | — | 单条消息附加写延迟 P95 ≤ 5ms（SAVEPOINT 内单行插入） |
| 分流数据可得性 | 无 | 可按 `disposition` 与 `reason_code` 聚合占比，支撑 Phase 2 收益测算 |
| 渠道无效重试 | 两条 409 各经历首次 attempt + 最多 4 次重试（默认 `max_attempts=5`，共最多 5 次 attempt）后 failed | 首次处理即 `processed`、`attempts=1`，不再有第二次 attempt，0 次重试 |

## 范围

**包含**：

- 路由决策数据模型与迁移（`0053_routing_decisions`）
- `send()` 改造：把隐式 `if` 链变成显式决策产出（**除 FR-3/FR-4 两处有意的行为变更外，不改变执行结果**）
- 人工请求规则（四语言、由客服能力持有配置、locale-agnostic 并集匹配、规则带显式 id；locale 仅作元数据，归一化后的 phrase 全局唯一）
- **两条 409 契约调整**：`conversation_closed` 与 `model_not_configured` 改为返回 `rejected` 结果而非抛异常，让决策记录能落库，并修掉渠道对永久性 409 的无效重试
- 决策查询接口（按会话 / 按租户聚合，含键集游标分页与时间跨度上限）
- `trace_enabled` 默认关闭；迁移与验证完成后，在指定 canary 环境显式开启并观察 7 天

**不包含**（属后续阶段或明确不做）：

- **事件发布** —— 本阶段不发布 `routing.decision_created`。它目前没有消费者，而发它需要回填决策 id、区分两条调用路径的真实提交点（渠道传外部连接时 `transaction()` 不提交），还会放大事件总线的既有 scope 缺陷。等有消费者且投递语义明确后再加
- `direct` / `lightweight` 执行档位 —— Phase 2 / Phase 3。**当前唯一实现的应答链路是 ReAct loop**（`core_platform/agent_runtime/engine.py`），不存在"不调模型的确定性应答"与"轻量检索应答"两条链路
- `Resume`（跨轮次恢复任务）—— Phase 4，依赖会话内任务模型
- `Escalate`（执行中升级处理主体或策略）—— Phase 3
- Core Platform 的 provider host 与执行档位循环 —— Phase 3（届时才有第二条执行路径）
- 会话内任务模型 `conversation_tasks` —— Phase 4
- Execution Profile 与预算管理 —— Phase 3
- 前端分流配置页 —— Phase 2 起（本阶段只提供查询接口）
- 模型分类器 —— 本阶段不使用任何模型参与路由判断
- **租户级覆盖人工请求规则** —— 现有 `CapabilityConfigService` 是平台级、无租户覆盖，本阶段只做环境变量级配置
- **可靠事件投递（Outbox）** —— 仓库目前没有 Outbox，且本阶段不发事件，不建消息可靠性基础设施

**本阶段与路径模型的关系**：除 FR-3/FR-4 两处有意变更外，Phase 1 只记录**已经存在的行为**，不新增任何路径。现有五个判断分支归并为 4 种业务处置（Reject / Handoff / Defer / Continue）；只有 `continue` 的 `execution_tier='agent'`，Reject / Handoff / Defer 均为 `NULL`。**不建任何预留列**（`task_relation` / `escalate_from` / `decision_type` / `stage_ids` / `confidence` / `profile_ref`）——语义未定型前建列，等于用未验证的抽象绑架后续阶段。

**顺带修复（与本阶段强相关，不依赖后续档位）**：

- 人工请求识别从"仅中文两个词"扩展到四语言规则集（问题 2），否则海外渠道的 Handoff 路径形同不存在
- **Reject 对渠道客户当前是静默的**：`conversation_closed` 抛出 409 后，渠道入站记录 `error_code`，并按首次 + 最多 4 次重试（默认 `max_attempts=5`）继续尝试直至失败，客户全程收不到任何回复。本阶段通过 FR-4 的契约调整**让决策能落库并停止无效重试**；客户可见的话术回复仍随 Phase 2 的 Direct 档一起补（固定话术，不需要 FAQ 数据）

## 风险与约束

- **误改行为的风险**：`send()` 是客服主链路，任何分支语义变化都会直接影响线上。缓解：决策产出与执行分离（先算决策、再按决策执行），并用 `reason_code` ↔ 原分支一一映射表 + 逐分支对照测试锁定等价性。
- **锁序风险**：`send()` 已固定"受理咨询锁 `pg_advisory_xact_lock(71432019)` → 会话行 `FOR UPDATE`"的顺序（第 116-128 行）。决策写入必须发生在同一事务、同一锁序**之后**，不得新开事务或提前取锁，否则可能引入反向锁序死锁。
- **写入成本**：每条消息一行。缓解：单行插入、索引按查询路径设计、开关可整体关闭；若后续量级上升，可改为异步事件汇聚（不在本阶段）。
- **数据生命周期**：本表**不存消息原文，也不存摘要**（SHA-256 对"退款/查订单"这类短文本可用字典还原，不构成脱敏）。只存 `message_length` 与 `request_id`。
- **事务语义风险**：观测写入失败若直接吞掉 Python 异常，PostgreSQL 事务已处于 aborted 状态，后续业务写入会全部失败——恰好在要保护的场景里打死主流程。缓解：用 `SAVEPOINT`（`begin_nested()`，本仓 `conversation/service.py:346` 已有先例）隔离。边界：连接断开或事务失效时 SAVEPOINT 同样无效，此时由既有错误处理决定请求失败，**不承诺绝对隔离**。
- **有意行为变更风险**：本阶段**不是零行为变更**。规则扩展会让 `human` / `real person` / `客服` 等消息从"继续走 Agent"变成"转人工"；两条 409 的返回契约也变了，开关无法回退这两项。缓解：在 01/02/05 明确列为有意变更，A3 单列验收，A8 要求产品确认"开关只关记录、不回退行为"。
- **事件延后风险**：本阶段不发事件，外部系统若依赖 `routing.decision_created` 将拿不到（目前无消费者）。登记为已知限制 L1。
- **Reject 契约变更风险**：`send()` 由抛异常改为返回 `rejected` 结果，两个调用方（HTTP messages 端点、渠道入站）必须同步；漏改会导致 409 变 200 或渠道继续重试。缓解：AC-1 / AC-7 / AC-12 锁定两个调用方。
- **兼容性**：新增表为纯追加，不改已有表结构；存量会话无需回填。**除 FR-3、FR-4 外**，其余分支在 HTTP 状态码与持久化副作用上与基线一致。
