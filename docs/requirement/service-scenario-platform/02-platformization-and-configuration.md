# 服务场景平台 · 配置化与平台化

> 状态：架构草案，待评审
> 核心决策：配置化和平台化作为 V1 产品骨架，不做事后返工式补丁

## 1. “一步到位”的定义

### 1.1 一步到位的范围

本文所说的一步到位，是指以下内容在 V1 就形成稳定设计和可验证闭环：

- 场景定义模型；
- 业务对象与业务事实契约；
- 用户决策与处理承接契约；
- 场景运行时；
- 管理端场景工作台；
- 版本、发布、审计和回滚；
- 决策追踪与指标口径。

第一版可以只支持少量场景和一种业务对象，但新增同类场景必须能够通过配置完成，而不是重新写页面和分支逻辑。

### 1.2 一步到位不等于一次做完所有业务

以下内容不应作为 V1 前置条件：

- 接入所有业务对象；
- 接入所有渠道；
- 支持所有处理承接类型；
- 提供任意表单设计器；
- 提供任意拖拽流程设计器；
- 自研通用 DSL；
- 让业务管理员配置底层路由表达式。

平台化的目标不是“什么都能配”，而是：

> **共性能力固定，业务差异配置，外部系统通过扩展点接入。**

## 2. 目标架构

```text
客户侧
服务目录 / 自然语言 / 对象卡片 / 外部入口
                    ↓
场景运行时
场景识别 → 对象解析 → 事实投影 → 交互决策 → 处理承接 → 决策追踪
                    ↑
版本化场景配置
                    ↑
管理端
目录管理 → 场景卡 → 实时预览 → 发布/回滚 → 指标
```

对应五层平台能力：

| 层 | 平台能力 |
|---|---|
| 配置层 | 服务目录、场景卡、对象、事实、决策、推荐、承接、兜底 |
| 运行时 | 场景解析、对象绑定、上下文构造、交互编排、承接路由 |
| Provider 层 | 对象查询、事实获取、知识检索、业务动作、人工队列 |
| 管理端 | 配置、预览、模拟、发布、版本、权限、审计 |
| 证据层 | 决策记录、上下文快照、执行结果、指标 |

### 2.1 与请求路由的关系

请求路由和服务场景平台是两个互补层次：

```text
请求路由
  决定：拒绝 / 转人工 / 延迟 / 继续
        ↓ continue
服务场景平台
  决定：进入哪个场景、围绕哪个对象、使用哪些事实、
        用户做哪些选择、由哪种承接方式处理
```

二者共享场景、对象和上下文，但职责不同：

- Routing 不负责订单列表、售后表单和业务对象查询；
- 场景平台不替代“会话关闭、黑名单、用户明确要求人工”等入口处置；
- `Direct` 是场景平台的承接类型之一，不是场景本身；
- 结构化 Interaction 和自然语言 Routing 可以走不同入口，但落到同一套场景与上下文。

## 3. 七个必须一次定稿的核心契约

### 3.1 场景定义契约

场景必须是一份可版本化、可发布、可回滚的配置，而不是散落在代码中的分支。

至少包含：

```text
场景 ID
版本
租户
适用渠道
客户任务
入口方式
业务对象类型及是否必需
展示事实
用户决策
推荐问题或动作
处理承接
异常兜底
指标口径
```

场景定义需要区分：

- 草稿；
- 待发布；
- 已发布；
- 已下线；
- 历史版本。

### 3.2 业务对象契约

业务对象在会话中只保存引用和必要展示信息，不复制完整业务快照。

对象契约至少表达：

```text
对象类型
对象 ID
对象候选集
对象实例
当前状态
权限边界
失效状态
```

对象列表是候选集视图，不是业务对象本身。平台必须区分：

- 对象类型：订单；
- 对象候选集：订单列表；
- 对象实例：订单 #A123；
- 对象引用：会话中保存的订单 ID。

### 3.3 业务事实投影契约

事实投影负责把业务系统数据转换为当前场景可展示、可授权使用的信息。

至少描述：

```text
字段来源
显示名称
展示顺序
格式化方式
是否脱敏
是否允许传给 Agent
是否允许传给人工
刷新策略
```

原则：

- 同一个对象在不同场景展示不同事实；
- 事实是投影，不是全量复制；
- 事实必须标记来源与新鲜度；
- 权限过滤发生在事实投影和对象解析之前，而不是展示之后再隐藏。

### 3.4 用户决策契约

每个决策点至少描述：

```text
决策 ID
决策类型
选项
是否必选
默认值
推荐排序
是否允许自由输入
是否允许跳过
是否二次确认
是否允许纠正
选择后的去向
```

必须区分：

- 系统决策：路由、分流、承接选择；
- 用户决策：选对象、选问题、确认提交、转人工。

任何有业务后果的用户动作都必须显式确认，并留下可审计记录。

### 3.5 处理承接契约

Direct、知识、查询、办理、Agent、人工、跟踪使用统一的承接契约。

统一输入：

```text
场景
对象引用
业务事实
用户决策
当前问题
会话上下文
```

统一输出：

```text
成功 / 失败 / 需补充 / 处理中
结果内容
下一步动作
是否可转人工
是否建立跟踪
```

Direct 只负责确定性回答，不负责对象查询或业务动作。

### 3.6 决策追踪契约

每次处理必须能够回答：

- 为什么进入这个场景；
- 为什么选中这个对象；
- 使用了哪些业务事实；
- 用户做了什么决策；
- 最终走了哪种承接；
- 为什么转人工；
- 结果是什么。

决策追踪不是日志字符串，而是结构化证据，至少包含：

```text
场景 ID 与版本
对象引用
事实快照（按授权范围）
用户决策
承接类型
处理结果
失败原因
人工队列
```

### 3.7 版本、租户与审计契约

从 V1 开始必须支持：

- 租户隔离；
- 配置草稿；
- 发布；
- 灰度；
- 版本对比；
- 回滚；
- 操作审计；
- 权限控制。

如果没有这些能力，配置化很快会变成“谁都能改、没人知道改了什么”的运维风险。

## 4. 配置化边界

### 4.1 三级能力

| 变更类型 | 落地方式 |
|---|---|
| 新增一个使用已有对象和已有承接方式的场景 | 纯配置，不写代码 |
| 新增一种业务对象或订单来源 | 新增 Provider + 配置 |
| 新增一种承接能力或外部系统动作 | 新增平台扩展点 + 配置 |
| 新增任意流程或页面布局 | 固定模板 + 有限扩展，不做万能流程引擎 |

### 4.2 配置化不等于低代码平台

允许配置：

- 服务目录；
- 场景卡；
- 对象策略；
- 事实字段；
- 推荐问题；
- 决策选项；
- 承接方式和兜底；
- 渠道与灰度；
- 指标口径。

不允许配置：

- 任意脚本；
- 任意 DSL；
- 任意跨系统调用顺序；
- 绕过权限的业务动作；
- 业务管理员直接修改底层路由表达式。

### 4.3 平台化验收测试

第一版最重要的验收标准是：

> **在不修改前端和后端代码的情况下，能够通过管理端新增第二个场景。**

例如：

1. 先配置“查询我的订单”；
2. 再只靠配置新增“咨询订单规则”；
3. 如果必须改代码才能新增第二个场景，说明平台化没有真正成立。

## 5. 运行时设计

建议运行时拆成六个稳定步骤：

```text
SceneResolver       识别场景
ObjectResolver      解析对象或候选集
FactProjector       投影业务事实
InteractionEngine   生成用户决策与推荐
HandlerRouter       选择处理承接
TraceRecorder       记录决策与结果
```

### 5.1 SceneResolver

输入：

- 用户消息；
- 入口；
- 渠道；
- 租户；
- 会话状态；
- 可能的对象上下文。

输出：

- 候选场景；
- 置信度或确定性依据；
- 需要补充的输入。

### 5.2 ObjectResolver

输入：

- 场景；
- 当前用户/业务主体；
- 候选对象类型；
- 用户已选对象。

输出：

- 对象实例；
- 对象候选集；
- 无对象状态；
- 失效状态；
- 权限不足状态。

### 5.3 FactProjector

输入：

- 对象引用；
- 场景；
- 展示字段配置；
- 权限上下文。

输出：

- 用户可见事实；
- Agent 可用事实；
- 人工可用事实；
- 脱敏结果。

### 5.4 InteractionEngine

输入：

- 场景；
- 对象状态；
- 事实；
- 决策配置；
- 推荐问题配置。

输出：

- 当前要展示的选项；
- 可点击的推荐问题；
- 需要用户确认的动作；
- 纠错和切换入口。

### 5.5 HandlerRouter

输入：

- 场景；
- 用户决策；
- 对象与事实；
- 承接策略。

输出：

- Direct / 知识 / 查询 / 办理 / Agent / 人工 / 跟踪。

### 5.6 TraceRecorder

输入：

- 场景识别结果；
- 对象绑定结果；
- 事实投影；
- 用户决策；
- 承接结果。

输出：

- 决策记录；
- 上下文快照；
- 指标事件；
- 管理端可读解释。

## 6. 管理端设计

### 6.1 五个固定工作区

1. **服务目录管理**
   - 业务域、场景、任务；
   - 图标、排序、渠道、可见范围；
   - 停用、灰度、复制。

2. **场景卡**
   - 基本信息；
   - 入口；
   - 对象；
   - 事实；
   - 决策；
   - 推荐；
   - 承接；
   - 兜底；
   - 指标。

3. **实时预览**
   - 模拟用户输入；
   - 模拟对象选择；
   - 查看推荐和承接；
   - 查看异常路径。

4. **发布与版本**
   - 草稿；
   - 预览；
   - 发布；
   - 灰度；
   - 版本对比；
   - 回滚；
   - 审计。

5. **决策解释与指标**
   - 最近决策记录；
   - 场景命中原因；
   - 对象绑定原因；
   - 转人工原因；
   - 转化率和解决率。

### 6.2 管理者需要看到什么

管理者不需要看到底层路由表达式的全部细节，但必须能回答：

1. 这个场景有哪些入口？
2. 哪些用户可以进入？
3. 围绕哪个业务对象？
4. 用户会看到哪些事实？
5. 用户能做哪些选择？
6. 系统会给出哪些推荐？
7. 哪些情况会转人工？
8. 出问题后怎么回滚？
9. 上线后效果如何？

### 6.3 场景模拟器

建议直接提供：

```text
输入用户问题
→ 选择或模拟业务对象
→ 显示命中场景
→ 显示展示事实
→ 显示推荐问题
→ 显示决策点
→ 显示承接方式
→ 显示兜底路径
```

模拟器必须能在发布前发现：

- 误分流；
- 错误对象；
- 空状态；
- 推荐问题不相关；
- 承接方式错误；
- 转人工队列错误。

## 7. 反模式

1. 先写死第一个场景，再承诺“以后配置化”。
2. 把场景平台做成任意拖拽流程设计器。
3. 把服务目录做成无限深菜单树。
4. 把订单列表当成业务对象本身。
5. 把订单整个快照复制进会话。
6. 强制所有场景先选订单。
7. 推荐问题使用全局静态 FAQ。
8. 转人工不带业务上下文。
9. 把底层路由表达式暴露给业务管理员。
10. 没有版本、灰度、审计和回滚就开放配置。

## 8. 结论

服务场景平台应以“场景卡 + 固定模板 + 可配置插槽”为核心，而不是“万能流程引擎”。

平台化一次到位的关键不是把所有业务做完，而是先固定：

```text
场景定义
对象契约
事实契约
决策契约
承接契约
证据契约
配置治理
```

在这些契约之上，第一个场景可以很小，但第二个场景必须能主要通过配置新增。这是判断平台化是否真正成立的核心标准。
