## 定位

本目录沉淀智能客服从“单次问答”走向“可配置业务场景平台”的产品模型和平台化方案。

它与请求路由的关系是：

- **请求路由**回答一条自然语言消息“该拒绝、转人工、延迟还是继续处理”；
- **服务场景平台**回答继续处理之后“围绕哪个业务、哪个对象、哪些事实、由什么能力完成”；
- 二者共享场景、业务对象和业务上下文，但不是两套互不相干的系统；
- Direct 不是孤立功能，而是服务场景平台中的一种处理承接方式。

## 核心判断

1. 共性不能做成一个万能客服页面，也不能一开始做任意拖拽流程设计器。
2. 正确形态是“通用场景壳 + 可配置场景卡 + 有限场景模板”。
3. 配置化和平台化应作为第一版产品骨架，而不是第一个场景完成后的补救。
4. “一步到位”指模型、契约、管理端、运行时和证据链一次设计并进入 V1，不要求一次接入所有业务。
5. 第一版以“查询我的订单/行程”完成闭环，再通过“咨询订单规则”验证纯配置复用。

## 当前边界

本目录目前是**产品与架构文档**，不代表代码已经实现。落地前仍需逐项评审：

- 场景配置的数据模型；
- 业务对象 Provider 的接入方式；
- 前端组件与现有客服壳的复用边界；
- Direct / 知识 / 查询 / 办理 / Agent / 人工的统一承接契约；
- 租户权限、版本发布、审计和指标口径。

## 关联结论

```text
服务目录 → 业务对象 → 业务事实 → 用户决策 → 处理承接
```

这条链不是必须顺序执行的五步流程，而是回答五个问题：

1. 用户从哪里找到任务；
2. 这次围绕哪个业务实体；
3. 需要看到哪些关键信息；
4. 用户需要明确选择或确认什么；
5. 谁来真正完成任务。
