# 服务场景平台 · 落地与验收

> 状态：实施规划草案，待评审
> 原则：同一套平台架构下分内部里程碑交付，不按“先 Demo、后平台化”的方式返工

## 1. 交付策略

采用“一次架构定稿，分里程碑验证”的方式：

```text
架构一次定稿
  ↓
核心契约一次定义
  ↓
管理端一次成型
  ↓
首个场景完整跑通
  ↓
后续场景只做配置和 Provider 扩展
```

所谓“一步到位”，是指平台骨架在 V1 就存在，不是指所有业务同时上线。

## 2. V1 范围

### 2.1 V1 必须包含

1. 场景定义与版本模型；
2. 服务目录配置；
3. 业务对象选择与对象引用；
4. 业务事实投影；
5. 用户决策与推荐问题；
6. Direct / 知识 / 查询 / Agent / 人工的统一承接入口；
7. 场景工作台；
8. 模拟与预览；
9. 草稿、发布、灰度、回滚；
10. 决策追踪与基础指标；
11. 租户隔离、权限和审计。

### 2.2 V1 可以少量实现

- 第一批只支持 1~2 种业务对象；
- 第一批只支持一个渠道或少量渠道；
- 第一批只完整支持 3 类场景模板：咨询型、查询型、办理型；
- 办理型可以先只支持一种动作；
- 跟踪可以先只支持状态展示，不要求完整通知体系。

### 2.3 V1 明确不做

- 任意拖拽流程设计器；
- 通用 DSL；
- 任意表单设计器；
- 所有业务对象 Provider；
- 所有外部系统接入；
- 任意 Agent 编排；
- 把底层路由规则暴露给业务管理员。

## 3. 里程碑

### 里程碑 1：平台骨架与查询场景闭环

目标：用平台方式跑通第一个完整场景。

交付：

- 场景定义模型；
- 服务目录；
- 业务对象类型与订单/行程对象；
- 对象列表和对象选择；
- 对象上下文卡；
- 业务事实投影；
- 对象相关推荐问题；
- Direct / 查询 / 人工承接；
- 决策追踪；
- 管理端只读或基础编辑能力；
- 实时预览。

首个场景：**查询我的订单/行程**。

验收：

- 用户能从自然语言、目录或对象入口进入；
- 用户能选择订单/行程；
- 页面明确显示当前绑定对象；
- 用户能纠正“不是这个对象”；
- 无对象时有出口；
- 转人工时带对象上下文；
- 管理端能解释一次处理为什么这样走。

### 里程碑 2：纯配置新增第二个场景

目标：验证平台抽象是否成立。

只通过配置新增：

- 咨询订单规则；
- 查询物流；
- 咨询发票规则。

验收：

- 不修改前端代码；
- 不修改后端场景分支代码；
- 复用已有对象选择、事实投影、推荐问题和承接能力；
- 管理端能模拟和发布；
- 发布后能回滚。

如果第二个场景必须写新页面或新增一套分支，说明平台化没有成立，应先修正抽象而不是继续加场景。

### 里程碑 3：办理型承接

目标：验证写操作、确认、回执和跟踪。

交付：

- 申请售后；
- 提交反馈；
- 办理表单；
- 二次确认；
- 提交回执；
- 处理中状态；
- 转人工；
- 结果指标。

验收：

- 用户明确确认后才提交；
- 提交后能看到回执；
- 处理中状态可见；
- 失败时有重试、转人工或留言；
- 人工能看到用户已提交的内容和业务对象。

### 里程碑 4：运营与治理闭环

目标：让配置可运营、可解释、可回滚。

交付：

- 场景指标；
- 决策解释；
- 版本对比；
- 灰度；
- 回滚；
- 审计；
- 异常分析；
- 租户级权限。

验收：

- 管理者能定位一次误分流；
- 能比较两个场景版本；
- 能灰度一个场景；
- 能回滚到上一个稳定版本；
- 能按场景、入口、渠道和对象类型查看指标。

## 4. 首个场景的验收清单

### 4.1 服务目录

- 业务域名称使用客户语言；
- 二级任务不超过用户可理解的范围；
- 目录中始终有“其他问题”或自由输入；
- 同一任务可以多入口，但共享同一场景配置。

### 4.2 业务对象

- 对象列表有筛选；
- 对象卡片有状态和识别事实；
- 有“查看更多”和“没有对应对象”；
- 对象选择不是所有任务的强制步骤；
- 对象权限在展示前完成过滤。

### 4.3 业务事实

- 对象卡片只展示必要事实；
- 事实有来源和刷新策略；
- 敏感字段脱敏；
- 不把完整业务快照复制到会话；
- 对象状态变化后能刷新。

### 4.4 用户决策

- 用户能明确选择对象；
- 用户能确认和纠正；
- 有后果的动作二次确认；
- 用户能切换对象或业务；
- 用户决策和系统决策记录分离。

### 4.5 处理承接

- Direct 不误用于需要查对象的场景；
- 查询失败有兜底；
- Agent 不自行猜测对象；
- 人工队列正确；
- 转人工携带场景、对象、事实和用户决策；
- 处理结果有明确下一步。

### 4.6 管理端

- 能配置目录；
- 能配置场景卡；
- 能模拟用户输入和对象选择；
- 能查看命中场景和承接路径；
- 能草稿、发布、回滚；
- 能查看决策记录和指标。

## 5. 平台化验收标准

以下标准应作为平台是否“一步到位”的硬性判断：

| 标准 | 验收方式 |
|---|---|
| 新增同类场景不改代码 | 用“咨询订单规则”验证纯配置接入 |
| 场景可版本化 | 草稿、发布、回滚全过程可验证 |
| 管理端可解释 | 任取一条决策记录，能说明场景、对象、事实、承接和原因 |
| 上下文可纠正 | 错选对象后能“不是这个对象/切换对象” |
| 失败可兜底 | 无对象、对象失效、查询失败、人工不可达均有路径 |
| 租户可隔离 | 一个租户的目录、场景、对象和指标不影响其他租户 |
| 能力可扩展 | 新对象通过 Provider，新承接通过扩展点，不改场景 UI |
| 结果可度量 | 能按场景、入口、对象类型、渠道查看转化和失败 |

## 6. 角色与职责

| 角色 | 主要职责 |
|---|---|
| 产品经理 | 定义服务场景、客户任务、对象策略、决策和成功指标 |
| 业务运营 | 维护目录、文案、推荐问题、场景排序和灰度 |
| 平台研发 | 场景模型、运行时、Provider、承接扩展点和治理能力 |
| 前端研发 | 通用场景组件、预览、管理端工作台 |
| 数据/运营分析 | 指标口径、决策分析、场景优化 |
| 客服/业务专家 | 人工队列、兜底策略、业务规则和话术审核 |

## 7. 关键风险

| 风险 | 后果 | 缓解 |
|---|---|---|
| 第一个场景写得过死 | 后续场景必须复制代码 | 第一个场景也必须走场景定义、对象和承接契约 |
| 过早做万能流程引擎 | 抽象过度、交付失控 | 固定模板 + 有限插槽，不做任意流程 |
| 配置没有版本和审计 | 线上无法定位和回滚 | V1 就提供版本、发布、回滚和审计 |
| 对象被复制成快照 | 状态不一致、权限泄漏 | 只保存对象引用，事实按需投影 |
| 管理端暴露底层规则 | 业务人员无法理解，误配置风险高 | 管理端只配置场景卡和业务语言 |
| 指标口径不统一 | 无法判断场景价值 | 场景上线前定义指标口径 |

## 8. 待评审决策

1. 第一批业务对象选订单、行程，还是两者都选？
2. 第一个承接方式先做 Direct，还是先做查询？
3. 管理端 V1 是完整可编辑，还是先只读、再小范围编辑？
4. 业务对象 Provider 采用配置接入、代码接入，还是两者结合？
5. 场景配置是平台级、租户级，还是平台模板 + 租户覆盖？
6. 人工队列映射由谁维护？
7. 推荐问题是运营配置、知识库生成，还是模型生成后审核？
8. 指标是否需要区分“自动化解决”和“用户声称解决”？

## 9. 最终验收画面

客户侧：

```text
找到任务 → 选对对象 → 看清事实 → 做出选择
→ 得到结果 → 失败可退 → 人工可接
```

管理侧：

```text
配置场景 → 模拟预览 → 发布灰度 → 查看证据
→ 分析指标 → 修改版本 → 回滚
```

只有这两条闭环都成立，服务场景平台才算真正落地。
