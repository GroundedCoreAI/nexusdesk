# 服务场景平台 · 产品模型与界面蓝图

> 状态：草案，待评审
> 目标：把三个案例中的共性沉淀为 NexusDesk 可复用、可配置的产品形态

## 1. 核心命题

三个案例共同说明，智能客服的竞争力不在于“聊天框有多像人”，而在于能否让用户：

1. 低成本找到自己能办的事；
2. 准确建立业务上下文；
3. 在对象、规则、执行和人工之间平滑切换。

因此，产品建模的基本单元不是“聊天会话”，也不是“流程图”，而是**服务场景**。

服务场景由五层组成：

```text
服务目录 → 业务对象 → 业务事实 → 用户决策 → 处理承接
```

这不是五个页面，也不是必须顺序执行的五步流程，而是回答五个产品问题：

| 层次 | 回答的问题 |
|---|---|
| 服务目录 | 用户从哪里找到任务？ |
| 业务对象 | 这次围绕哪个实体办？ |
| 业务事实 | 为了确认对象和做决定，需要看哪些信息？ |
| 用户决策 | 用户需要选择、确认或授权什么？ |
| 处理承接 | 谁来真正把这件事办完？ |

## 2. 五层产品模型

### 2.1 服务目录

**定义：** 面向用户的业务发现层，按客户能理解的业务结构组织客服能力。

推荐结构：

```text
业务域 → 服务场景 → 客户任务
```

示例：

```text
购物消费 → 订单服务 → 查询我的订单
购物消费 → 订单服务 → 咨询订单规则
账号服务 → 账号安全 → 找回账号
```

**界面形态：**

- 业务域卡片；
- 分类面板；
- 二级任务选择；
- 猜你想问；
- 自由输入；
- “其他问题”出口。

**作用：**

- 让用户看见能力边界；
- 用业务语言降低表达成本；
- 把模糊问题带到具体任务；
- 为管理者提供可维护的能力地图。

**边界：**

- 目录负责“找到任务”，不负责“完成任务”；
- 目录不是后台技术模块清单；
- 目录不是无限深的菜单树；
- 目录不是决策树；
- 同一任务可以有多个入口，但不能复制出多套场景。

**管理端配置：**

- 业务域、场景、任务名称；
- 图标、描述、排序；
- 适用渠道；
- 展示位置和可见范围；
- 停用、隐藏、灰度。

### 2.2 业务对象

**定义：** 客户任务所围绕的业务实体。

典型对象：

- 订单；
- 行程；
- 会员；
- 账号；
- 优惠券；
- 创作内容；
- 举报对象；
- 店铺；
- 工单。

**对象关系必须分清：**

| 概念 | 含义 | 例子 |
|---|---|---|
| 对象类型 | 一类实体 | 订单 |
| 对象候选集 | 多个对象的集合视图 | 订单列表 |
| 对象实例 | 具体一条记录 | 订单 #A123 |
| 对象引用 | 会话中保存的对象定位 | 订单 #A123 的 ID |

“订单列表”不是业务对象本身，而是对象选择器；“一笔订单”是对象实例，不是业务事实。

**对象使用方式：**

| 方式 | 含义 | 例子 |
|---|---|---|
| 不需要对象 | 通用规则问题 | 会员如何购买 |
| 隐式对象 | 使用当前账号、当前会员、当前会话 | 查看账号状态 |
| 可选对象 | 有对象更准确，没有对象也能回答 | 订单规则咨询 |
| 必需对象 | 不绑定对象就无法处理 | 这笔行程费用有问题 |
| 多对象选择 | 同一用户有多个候选对象 | 订单列表、近期订单卡片 |

**产品原则：**

- 对象是上下文锚点，不是完整快照；
- 只展示用户有权访问的对象；
- 对象选择不是所有场景的强制步骤；
- 必须有空状态、失效状态和纠错路径。

**管理端配置：**

- 对象类型；
- 是否必需；
- 获取方式；
- 候选排序；
- 空状态和失效处理；
- 对象权限边界。

### 2.3 业务事实

**定义：** 当前场景下，从业务对象中取出并展示的最少必要信息。

事实不是对象本身，也不是全量数据：

```text
订单 #A123              ← 对象实例
状态：已发货             ← 事实
金额：299 元             ← 事实
下单时间：10 月 20 日     ← 事实
```

**事实的三个用途：**

1. 确认对象：是不是我要找的那一单；
2. 支持决策：能不能退款、开发票、投诉；
3. 支撑承接：给查询、Agent 或人工提供上下文。

**事实的分类：**

| 类型 | 说明 | 例子 |
|---|---|---|
| 识别事实 | 帮用户确认对象 | 时间、地点、名称、金额 |
| 状态事实 | 说明对象当前状态 | 已发货、已关闭、处理中 |
| 处理事实 | 支撑某个动作 | 退款期限、开票状态、是否可修改 |

**与知识、数据的区别：**

- 原始数据：业务表里的全部字段；
- 业务事实：当前场景需要展示和使用的字段；
- 知识：通用规则，例如“发票多久开具”；
- 会话上下文：对象引用、用户决策和必要事实的组合。

**管理端配置：**

- 展示哪些字段；
- 字段顺序和格式；
- 是否脱敏；
- 哪些字段用于推荐；
- 哪些字段可传给 Agent；
- 哪些字段可传给人工；
- 刷新和失效策略。

### 2.4 用户决策

**定义：** 用户在产品中需要明确做出的选择、确认或授权。

常见决策：

- 选择问题域；
- 选择具体任务；
- 选择订单或行程；
- 选择具体问题；
- 确认“是这个对象”；
- 纠正“不是这个对象”；
- 提交退款、售后或反馈；
- 选择继续咨询、转人工或结束；
- 切换订单或业务。

**系统决策与用户决策必须分开：**

| 类型 | 谁决定 | 例子 |
|---|---|---|
| 系统决策 | 平台/模型/规则 | 关闭会话、识别转人工、选择承接方式 |
| 用户决策 | 用户 | 选哪一单、问什么、是否提交、是否转人工 |

系统可以推荐、排序、预选，但不能替用户做有后果的选择。

**决策点设计原则：**

- 在用户具备足够信息时再出现；
- 不强制用户回答与当前任务无关的问题；
- 重要动作必须二次确认；
- 允许返回、纠正和切换；
- 允许自由输入兜底。

**管理端配置：**

- 决策点；
- 选项；
- 是否必选；
- 默认值和推荐排序；
- 是否允许跳过；
- 是否二次确认；
- 选择后的去向。

### 2.5 处理承接

**定义：** 用户做出选择后，真正完成任务的能力。

| 承接方式 | 做什么 | 例子 |
|---|---|---|
| Direct | 直接返回确定性内容 | 服务时间、购买方式、固定回执 |
| 知识回答 | 检索 FAQ、规则、文档 | 会员权益、发票规则 |
| 查询 | 读取订单、行程、物流、余额 | 查询订单状态 |
| 办理 | 提交退款、申诉、反馈、设置 | 申请售后、修改接单设置 |
| Agent | 多步推理、调用多个工具 | 复杂争议、跨系统问题 |
| 人工 | 带上下文转接或留言 | 接入“打车·乘客”客服 |
| 跟踪 | 记录任务状态、进度和通知 | 投诉进度、退款进度 |

**承接输入：**

```text
服务场景
+ 对象引用
+ 必要业务事实
+ 用户决策
+ 当前问题
+ 会话上下文
```

**承接输出：**

```text
成功 / 失败 / 需补充 / 处理中
+ 结果内容
+ 下一步动作
+ 是否可转人工
+ 是否建立跟踪
```

**边界：**

- 承接不是“回复一句话”；
- 转人工必须带场景和对象上下文；
- 失败、无权限、超时和服务不可用都是正常承接路径；
- Direct 不是独立业务，而是承接类型之一。

## 3. 客户侧界面蓝图

### 3.1 可复用界面能力

| 组件 | 承载层次 | 作用 |
|---|---|---|
| 服务目录组件 | 服务目录 | 业务域、场景、任务导航 |
| 推荐问题组件 | 服务目录/场景 | 降低表达成本 |
| 对象选择器 | 业务对象 | 列表、筛选、选择、空状态 |
| 对象上下文卡 | 业务事实 | 展示当前绑定对象和关键事实 |
| 决策区 | 用户决策 | 选项、确认、纠正、切换 |
| 承接结果区 | 处理承接 | 回答、查询结果、办理回执、转人工 |
| 兜底区 | 全链路 | 其他问题、无结果、切换、人工 |

### 3.2 三类场景模板

#### 模板 A：咨询型

```text
目录/推荐问题 → 知识回答 → 继续追问/转人工
```

适用：

- 会员如何购买；
- 发票规则；
- 账号规则；
- 创作指南。

#### 模板 B：查询型

```text
对象选择 → 对象上下文 → 动态问题 → 查询结果 → 兜底/转人工
```

适用：

- 查询我的订单；
- 查询行程；
- 查询物流；
- 查询退款进度。

#### 模板 C：办理型

```text
对象选择 → 问题确认 → 表单 → 二次确认 → 提交回执 → 跟踪
```

适用：

- 申请售后；
- 提交举报；
- 修改设置；
- 反馈问题。

“选择型”不是单独模板，而是查询型和办理型共用的对象选择能力。

### 3.3 客户侧原则

- 结构化入口和自由输入始终并存；
- 目录不是唯一入口；
- 对象选择不是所有场景的强制步骤；
- 绑定对象后必须展示摘要；
- 绑定对象后必须允许纠正和切换；
- 推荐问题必须随对象和状态变化；
- 失败、无结果和转人工都是一等路径。

## 4. 管理端形态

管理端不做“路由规则编辑器”，也不做任意拖拽流程设计器。建议做成“场景工作台”：

```text
┌─────────────┬────────────────────────┬─────────────┐
│ 服务目录树   │ 场景配置                │ 实时预览     │
│             │                        │             │
│ 购物消费     │ 基本信息                │ 手机界面     │
│  查询订单    │ 入口与目录              │ 模拟用户输入 │
│  咨询规则    │ 业务对象                │ 查看命中场景 │
│  申请售后    │ 展示事实                │ 查看处理路径 │
│             │ 用户决策                │             │
│ 账号服务     │ 推荐问题/动作            │             │
│             │ 处理承接与兜底           │             │
│             │ 指标                    │             │
└─────────────┴────────────────────────┴─────────────┘
```

管理端必须回答五个问题：

1. 有哪些场景？
2. 用户怎么进入？
3. 系统围绕哪个对象回答？
4. 为什么这样处理？
5. 效果如何？

管理端核心能力：

- 服务目录管理；
- 场景卡配置；
- 实时预览与模拟；
- 草稿、发布、灰度和回滚；
- 决策解释；
- 指标看板。

## 5. 首个标杆场景：查询我的订单/行程

推荐流程：

```text
入口
  ├─ 自然语言“查我的订单”
  ├─ 首页/订单页入口
  └─ 近期对象卡片
        ↓
确定业务域（可选）
        ↓
展示候选对象（近期优先 + 筛选 + 查看更多）
        ↓
用户选择对象
        ↓
显示“正在咨询此对象” + 最小事实摘要
        ↓
基于对象状态推荐问题
        ↓
Direct / 知识 / 查询 / 办理 / Agent / 人工
        ↓
结果、继续咨询、切换对象或人工
```

关键产品决策：

1. 不把“订单问题”作为一个场景。
2. 拆分“查订单”“问规则”“办售后”“反馈服务”等任务。
3. 对象列表必须展示状态。
4. 对象卡片只放识别事实。
5. 绑定后显示摘要和纠正入口。
6. 必须有“没有对应订单”和“不是这个订单”。
7. 推荐问题随对象状态变化。
8. 转人工携带场景、对象引用、用户已选问题和必要事实。

## 6. 成功标准

首个场景上线后，应能回答：

- 用户能否找到订单入口？
- 用户能否快速选对订单？
- 绑定后是否知道当前咨询的是哪一单？
- 推荐问题是否与当前对象相关？
- 无订单、错订单、对象失效时是否有出口？
- 转人工是否携带上下文？
- 管理端是否能解释一次分流？
- 是否能在不改代码的情况下增加第二个场景？
