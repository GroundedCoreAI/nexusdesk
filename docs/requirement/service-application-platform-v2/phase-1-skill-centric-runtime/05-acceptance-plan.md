## 1. 验收目标与组织

确认 Phase 1 同时做到：

- **功能正确**：AC-1～AC-12 可实际复现。
- **业务有效**：应用配置概念收敛，运营能从示例复制到首次预览。
- **应用隔离可信**：同名技能/同一 Agent 多应用无串线，发布与渠道版本可追溯。
- **安全可上线**：凭据不明文落库/落日志，发布可回滚，失败可定位。
- **clean-break 完成**：旧概念、旧路由和旧双轨代码不再运行。

| 角色 | 职责 |
|---|---|
| 产品负责人 | 主持验收；判断概念收敛与运营体验；P2 遗留签字 |
| 研发负责人 | 提供环境、发布版本、指标数据和缺陷修复 |
| QA | 执行 AC、记录证据、回归与缺陷分级 |
| 渠道管理员代表 | 验证渠道绑定、版本切换与线上消息路径 |
| 安全/运维代表 | 核对凭据、审计、迁移、备份与部署边界 |

## 4. UAT 判定

由产品负责人与渠道管理员代表共同判定：

1. 服务应用详情是否比旧“场景/能力”模型更容易理解。
2. 从标准案例复制、配置连接、预览发布是否无需产品/研发口头解释即可完成。
3. 示例与应用、草稿与线上、应用版本与渠道版本的关系是否在界面上清晰可见。
4. 技能编辑抽屉的信息密度是否可接受，安全规则是否不会让人误以为需要编写代码。
5. 移除行业能力独立入口后，标准案例作为应用来源筛选是否符合日常工作流。

任何“需要研发解释才能完成基本配置”的问题至少记为 P2；影响发布或渠道正确性的问题记为 P1。

## 7. 通过标准与签字

- **通过**：A1～A12 全部通过；结构性与安全硬指标达成；C1～C7 全部通过；无 P0/P1 遗留。
