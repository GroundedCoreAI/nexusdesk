# Phase 1 · 技能中心的应用运行时 — 业务目标

> 状态：需求基线已落地，定向实现与验证完成；全量验收待执行
> 创建：2026-11-11
> 依据：主题 [README](../README.md)；现有服务应用、Provider、场景、行业包与渠道代码核查（迁移至 `0057_industry_pack_runtime`）
> 预估：约 3～4 周；包含上线前一次性破坏式重构

## 要解决的问题

### 问题 1：服务应用没有成为真正的业务边界

`backend/src/agent_platform/business_capabilities/customer_service/service_apps/models.py` 的 v1 配置把 Agent 当作 `capabilities` 中的一种类型，同时保留 `scenarios`、`capabilities` 和 `default_execution_order`。运营人员必须理解“应用 → 场景 → 能力 → Agent”多层关系，才能完成一次业务配置。

典型受损场景：两个服务应用都需要“订单查询”，但订单系统地址、鉴权、确认规则不同。当前模型只能建设同名/全局 Provider 或在场景中引用全局 Tool，无法明确表达“同一技能、不同应用、不同连接”。

### 问题 2：连接不是应用资产，隔离和授权无法证明

`service_provider_registry` 只有租户/业务/工作区维度，没有 `application_id`。真实 URL、Header 和凭据位于 `registered_tools` / `tool_credentials`，而场景又可通过 `ScenarioToolBridge` 引用这些全局资源。

典型受损场景：应用 A 配置订单查询后，应用 B 或同一 Agent 的其他应用可能看到不该使用的全局工具；审计也无法回答“这次调用属于哪个应用版本、哪个应用连接”。

### 问题 3：发布版本没有约束真实入口

应用虽然有 `service_application_versions`，但 `channels` 仍直接存 `agent_id`，`runtime_conversations` 也只记录 `agent_id`。渠道入站消息绕过了服务应用发布版本，导致“草稿修改不影响线上”“回滚应用版本”等承诺无法在真实渠道成立。

典型受损场景：运营回滚应用后，渠道新消息仍按 Agent 当前发布版本运行；排查时无法从会话定位应用版本。

### 问题 4：中间概念和历史机制过重

场景、Provider、接入能力、行业包安装、升级预览、升级冲突与升级记录共同形成第二套生命周期。用户需要理解平台内部抽象，却不能更快完成“复制案例 → 配连接 → 绑定渠道 → 预览发布”。

典型受损场景：行业案例被直接编辑后无法恢复；升级记录与合并逻辑增加维护成本，却没有对应的正式上线需求。

### 问题 5：前后端职责与页面边界失控

后端 `ServiceApplicationService` 达 1485 行，渠道服务 1019 行；前端 `ServiceAppsPage.tsx` 达 2384 行，`IndustryCapabilitiesPage.tsx` 达 1021 行。应用配置、场景调试、行业模板、Provider 配置与发布状态交织，任何调整都容易互相破坏。

## 业务目标

| 目标 | 说明 |
|---|---|
| G1：服务应用成为唯一业务交付主体 | 每个应用直接绑定一个 Agent 版本，并拥有自己的技能、连接、规则与客户渠道；不再通过场景/能力间接表达 |
| G2：技能与连接按应用完全隔离 | 同一应用内技能 key 唯一；不同应用可使用同名技能但指向不同连接、凭据和安全规则；运行时只能解析本应用授权资源 |
| G3：发布不可变且可追溯 | 发布生成 v2 快照；草稿修改不影响线上；回滚产生新的历史版本；渠道、入站事件、会话和运行都记录应用版本 |
| G4：标准案例可安全复用 | 标准案例以不可变示例应用存在，只能预览和复制；复制后成为用户应用；启动 seed 永不覆盖用户修改 |
| G5：概念和界面收敛 | UI 主概念收敛为服务应用、Agent、技能、应用连接、客户渠道；应用内部按概览/智能体/技能/业务规则/预览与调试/客户渠道与发布组织 |
| G6：上线前 clean-break | 删除 Provider、Scenario、执行能力、接入能力、升级记录及旧 API/UI/表引用；不提供旧数据迁移、双读或兼容层 |

## 成功指标

| 指标 | 基线（现状） | 目标 |
|---|---|---|
| 应用业务配置中的旧中间概念数 | 场景、能力、Provider 等至少 3 类仍参与主流程 | 新 UI/API/运行时中为 0；仅保留五主概念 |
| 同名技能跨应用配置能力 | 不支持应用级连接，无法证明隔离 | 两个应用同名技能指向不同 URL/凭据的集成用例 100% 通过 |
| 跨应用技能/连接泄露 | 无自动化保证；全局工具桥存在旁路 | 安全与集成测试 0 泄露，含同一 Agent 被多个应用引用场景 |
| 渠道消息可追溯应用版本 | 当前渠道与会话只记录 Agent | 入站事件、会话、运行的应用版本记录覆盖率 100% |
| 草稿修改影响线上版本 | 渠道绕过应用发布，无法保证 | 发布后修改草稿的线上行为 diff 为 0；重新发布后切换 |
| 标准案例被直接修改或重启覆盖 | 行业安装与升级链路允许复杂修改/合并 | 示例应用编辑请求 100% 被拒绝；重启不覆盖用户应用 |
| 从复制案例到首次预览完成时间 | 无正式基线 | UAT 5 名运营样本中位数 ≤ 10 分钟 |
| 旧概念代码残留 | 后端和前端的 Provider/Scenario/升级路由与组件仍存在 | 指定清理范围搜索结果为 0（允许历史文档与迁移文件） |
| 应用主页面单组件规模 | `ServiceAppsPage.tsx` 2384 行 | 拆分后单个新增/改造页面组件 ≤ 800 行，业务区块独立 |
| 应用列表可浏览规模 | 当前 `/service-apps` 返回全部，无分页 | 默认每页 10 条，服务端分页与 Ant Design Table/Pagination 一致 |

## 范围

**包含：**

- 应用直接绑定 Agent 与版本。
- 应用技能、应用连接、连接凭据的安全存储与 CRUD。
- v2 发布快照、发布检查、不可变版本、回滚、差异摘要。
- 应用级运行时解析与 Agent 工具白名单收口。
- 渠道、入站 outbox、会话与运行固定应用版本。
- 标准案例 seed、不可变示例、复制为我的应用。
- 应用列表分页、应用内部信息架构、技能表格与连接测试。
- 删除旧 Scenario/Provider/Industry Installation/Upgrade 的后端、前端、API、测试与类型。
- `0058_service_application_v2` 一次性破坏式迁移与新库初始化验证。
- 中英文、权限、审计、可观测和安全测试。

**不包含：**

- 不做旧数据转换、兼容 API、双读双写或旧路由重定向。
- 不做通用拖拽流程编排器。
- 不做外置意图 Router。
- 不做行业包安装实例、升级预览、三方合并或升级记录。
- 不在本阶段建设复杂规则 DSL；业务规则先采用技能级确定性字段与应用级兜底配置。
- 不做跨应用共享连接、共享凭据或公共业务对象 Template。
- 不做 Phase 2 的批量渠道灰度、自动流量切换和高级运营分析。

## 风险与约束

- **破坏式迁移风险**：`0058` 会删除旧服务场景/Provider/行业安装表。缓解：明确本项目尚未上线，升级前备份开发库；新库一次初始化和回归必须作为发布门槛。
- **运行时旁路风险**：只要仍允许 Agent 直接引用 `registered_tools`，应用隔离就不成立。缓解：客户应用运行时只接受发布快照中的应用技能；全局工具目录保留管理与调试用途，不直接授权给应用。
- **凭据泄露风险**：连接编辑和发布最容易把密钥写入 JSON 或日志。缓解：数据库只存 Vault 密文，发布只存 `credential_ref` 与 digest，API 只返回 `credentials_configured`。
- **渠道版本管理复杂度**：渠道显式固定版本，发布后不会自动切换。缓解：UI 清晰显示“当前绑定版本”，切换版本作为独立审计操作；Phase 2 再做批量/灰度。
- **示例与应用混淆**：用户可能误以为可直接修改标准案例。缓解：示例卡片固定标识、编辑按钮禁用、只提供“复制为我的应用”，复制后来源仅作 lineage。
- **能力边界扩张**：团队可能再次把通用业务流程塞入应用层。缓解：技能只表达一个明确业务动作；复杂决策仍由 Agent 推理，安全边界由确定性字段保证。
- **兼容性**：不保证旧服务应用配置可用；开发数据库需清空。部署必须应用代码、前端和 `0058` 迁移同一版本，不允许滚动混部。
