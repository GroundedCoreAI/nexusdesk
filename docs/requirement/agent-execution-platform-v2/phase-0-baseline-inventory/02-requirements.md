# Phase 0 · 基线与盘点 — 需求文档

> 状态：待评审（未开始实施）
> 创建：2026-11-02
> 依据：`01-business-goals.md`（G1–G3）、架构文档第 17 节 Phase 0

## 用户故事

**US-1（平台研发）**：作为执行平台研发，我希望看到经代码核验的调用和状态图，以便拆分契约时不遗漏隐式依赖。

**US-2（QA）**：作为 QA，我希望有一组可重复的现有行为测试和结果基线，以便准确识别后续重构回归。

**US-3（租户管理员）**：作为现有 Agent 的管理员，我希望历史草稿和已发布版本继续加载，以便平台演进不要求批量手工改配置。

**US-4（架构评审人）**：作为评审人，我希望标识、范围和未决项有唯一记录，以便后续阶段使用同一套术语和入口条件。

## 功能需求

### FR-1 目标提交与依赖盘点

| 项 | 说明 |
|---|---|
| 触发时机 | Phase 0 启动；每个后续阶段启动前增量复核 |
| 输入 | 干净目标提交、后端模块与测试、相关部署/配置入口 |
| 输出 | 提交 SHA、模块依赖图、公开/内部接口、owner、测试映射与差异记录 |
| 执行方式 | 静态代码核查为主，辅以最小运行验证；不得依据旧文档直接认定现状 |
| 失败处理 | 无法核验的依赖标为 `unknown`，指定 owner；阻断 Phase 1 的项不得留空 |

### FR-2 Run 生命周期与事件语义基线

| 项 | 说明 |
|---|---|
| 触发时机 | 依赖盘点期间及回归测试设计前 |
| 输入 | Repository/Worker/Engine、API/SSE 代码及现有测试 |
| 输出 | 所有可达状态转换、终态保护、取消/超时/失租流程、事件类型/排序/重放/瞬态差异 |
| 执行方式 | 代码路径与测试证据双向核对；不以理想状态图替代实际行为 |
| 失败处理 | 代码与文档不一致时以代码和运行证据登记既有行为，架构目标另列，不混写 |

### FR-3 Agent 配置与发布快照兼容样本

| 项 | 说明 |
|---|---|
| 触发时机 | 回归基线建立时 |
| 输入 | 经授权脱敏的历史配置、已发布快照及缺省/边界/非法构造样本 |
| 输出 | 版本化 fixture、预期规范化结果、加载/发布/快照断言与样本覆盖清单 |
| 执行方式 | 在现有 `AgentConfig` 和发布链路中自动加载，不写入新 Engine 默认值来修改原样本 |
| 失败处理 | 既有加载失败单独记录并保留 fixture；非法样本必须明确拒绝，敏感原文不得入库 |

### FR-4 现有执行行为回归基线

| 项 | 说明 |
|---|---|
| 触发时机 | Phase 0 内建立；后续阶段每次变更执行适用子集 |
| 输入 | 确定性 mock 模型/工具、PostgreSQL fixture、配置样本和事件消费者 |
| 输出 | ReAct 成功/失败/预算、队列/租约/取消/终态、事件/SSE、配置兼容测试及基线报告 |
| 执行方式 | CI 可重复自动执行；时间不依赖真实等待，外部服务不进入必过路径 |
| 失败处理 | 失败、skip、xfail、flaky 均记录原因；不得通过放宽断言取得“全绿” |

### FR-5 标识与首次迁移约定

| 项 | 说明 |
|---|---|
| 触发时机 | Phase 1 契约编写前 |
| 输入 | 架构中的 Engine/Protocol/Adapter 示例和现有 React 实现 |
| 输出 | 初始标识 `(react,native,v1)`、LocalTestAdapter 测试标识约定、版本格式、Run=一次 Execution 的说明 |
| 执行方式 | 架构评审后冻结为基线；新增标识走注册与兼容校验，不在 Worker 写分支 |
| 失败处理 | 命名冲突或语义不清在 Phase 0 解决；未决项不得被实现自行隐式决定 |

### FR-6 基线度量与重构检查清单

| 项 | 说明 |
|---|---|
| 触发时机 | 回归测试稳定后、Phase 0 验收前 |
| 输入 | 两次干净环境执行结果、覆盖率、测试耗时、已知缺陷和后续设计问题 |
| 输出 | 可复现命令、测试/覆盖率/耗时基线、缺陷清单、分阶段回归映射和重构检查清单 |
| 执行方式 | 同一提交与环境连续执行 2 次；记录环境差异，不将缺失数据填成 0 |
| 失败处理 | 非确定结果必须定位或隔离并标注；P0/P1 未决项阻断 Phase 1 |

本阶段不新增运行时配置开关或数据库字段。

## 非功能需求

- **可复现**：文档记录提交、命令、环境与 fixture 版本；测试结果不依赖外部模型或真实等待。
- **兼容**：不得为适配未来模型修改现有配置 JSONB、Run 表或公开 API；本阶段无迁移。
- **安全**：样本脱敏且最小化；日志、fixture、报告中不得出现 Token、连接串或可识别客户数据。
- **可维护**：基线测试只断言已评审的公开/关键内部行为，避免无意义绑定私有实现细节。
- **性能**：基线测试沿用现有 CI 资源；实际耗时先测量，若超过既有预算须单独评审，不预设虚假数值。

## 验收标准

| # | 场景 | 预期 |
|---|---|---|
| AC-1 | 对锁定提交检查核心执行与配置模块，并沿一条 Run 创建到终态链路追踪 | 依赖图覆盖 FR-1 全部入口；每条边可定位代码；无未分派的关键 unknown |
| AC-2 | 对照代码与测试执行正常、取消、超时、失租和重复终态场景 | 生命周期与事件清单覆盖所有可达路径；实际行为与目标行为分栏；证据完整 |
| AC-3 | 加载全部历史脱敏、缺省、边界和非法 Agent 配置样本 | 合法样本按既有规则通过，非法样本明确失败；样本未被迁移或改写；敏感信息扫描通过 |
| AC-4 | 在干净环境对同一提交连续运行两次基线套件并查看 CI 证据 | 结果一致；所有 skip/xfail/flaky 有解释；失败未被弱化断言隐藏 |
| AC-5 | 用冻结标识编写后续 Phase 1 的示例并评审 Run/Execution 术语 | 示例统一使用 `(react,native,v1)`；无 Worker 引擎分支或第二套术语；未决命名均有裁定 |
| AC-6 | 检查基线报告与重构检查清单后召开 Phase 1 入口评审 | 命令、覆盖率、耗时、缺陷和回归映射齐全；P0/P1 阻断项为 0，其他项均有 owner 与期限 |
