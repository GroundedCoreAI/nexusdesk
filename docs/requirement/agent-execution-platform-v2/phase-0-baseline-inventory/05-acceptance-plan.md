# Phase 0 · 基线与盘点 — 验收方案

> 状态：待实施（Phase 1 启动前执行）
> 创建：2026-11-02
> 依据：`01-business-goals.md`（G1–G3、成功指标）、`02-requirements.md`（AC-1–AC-6）；测试依据见 `04-test-plan.md`

## 1. 验收目标与组织

确认基线**真实可溯**、兼容样本**可重复加载**、回归结果**确定可复用**，并确认 Phase 1 可以在无 P0/P1 基线阻断项的条件下启动。

| 角色 | 职责 |
|---|---|
| 架构负责人 | 主持评审；裁定依赖边界、实际/目标行为差异和标识 |
| 产品负责人 | 确认存量 Agent 不需手工迁移的范围承诺与 P2 遗留 |
| QA | 执行 AC、双跑对比、缺陷分级与证据归档 |
| 研发负责人 | 提供干净环境、CI/覆盖率/耗时数据和未决项修复 |
| 安全代表 | 审核历史样本脱敏与报告敏感信息边界 |

## 2. 验收环境与前置条件

| 环境 | 用途 |
|---|---|
| 锁定提交的干净后端工作树 | 代码证据、文档与 diff 核查 |
| 项目既有 PostgreSQL 集成环境 | 生命周期、事件、配置发布与 SSE 场景 |
| 干净 CI 环境（同一提交两次） | 可复现性、覆盖率与耗时基线 |

**前置条件**：`04-test-plan.md` 全部适用用例通过；无 P0/P1 未关闭；历史样本已授权、脱敏并有清单；所有 `pending_env` 已指定验收环境和 owner，不得默认豁免。

## 3. 功能验收清单（对应 AC-1–AC-6）

| # | 验收步骤 | 通过判据 |
|---|---|---|
| A1 | 从 Run API/Composition 沿创建、认领、执行、事件和终态路径追踪，并逐项抽查依赖图证据 | AC-1：所有核心入口和调用边可定位代码/测试；owner 与测试映射齐全；无未分派关键 unknown |
| A2 | 执行或查看正常、queued/running 取消、超时、失租、重复 finish/迟到事件场景，对照生命周期清单 | AC-2：所有代码可达路径有实际行为与证据；目标差异另列；终态保护无反例 |
| A3 | 运行全部合法/非法历史配置样本及草稿→发布→快照链路，并扫描 fixture/报告 | AC-3：合法样本按现状加载、非法样本明确失败、源数据未改写；跨租户不可读；扫描无秘密 |
| A4 | 在同一干净 CI 环境连续执行两次基线套件，比较测试节点、skip/xfail、计数和报告 | AC-4：节点级结果一致；所有例外有原因和 owner；CI 原始日志与命令可追溯，无弱断言掩盖 |
| A5 | 评审标识表、LocalTestAdapter 命名约束和 Phase 1 示例，检查 Run/Execution/Task 术语 | AC-5：统一 `(react,native,v1)`；Run=一次 Execution；无 Task 双表、Worker 分支或未裁定命名 |
| A6 | 逐项检查基线报告、缺陷清单和 Phase 1–7 重构检查清单，召开入口评审 | AC-6：命令/环境/覆盖率/耗时/CI/回归映射完整；P0/P1 为 0；其他项有 owner 和期限 |

每个场景记录：执行人、日期、目标 SHA、环境、前置数据、实际结果、判定、测试节点及 CI/截图链接。

## 4. UAT 判定（架构与 Agent 配置代表）

- 架构代表确认依赖图能回答“新增一个 Adapter 需要改哪些入口”，且不把架构目标误写成当前实现。
- Agent 配置代表抽查典型历史草稿和已发布版本，确认本阶段未要求手工添加 Engine 字段。
- QA 与研发共同确认基线失败不会被后续阶段自动视为“可接受回归”。

## 5. 业务指标验收

| 指标 | 基线 | 目标 | 测量方法 |
|---|---|---|---|
| 核心模块盘点覆盖率 | 无统一清单 | 100% | 按 FR-1 模块清单逐项核对 owner、调用关系、数据/事件和测试映射；缺失即未达标 |
| 状态转换与公开事件语义覆盖率 | 分散 | 100% | 从代码可达路径生成清单，与 A2 测试证据逐条勾销；未知单列且不得计为覆盖 |
| 纳入样本的配置加载通过率 | 待 Phase 0 测量 | 100%，既有失败须裁定 | 对全部版本化 fixture 执行；分母固定，不得删除失败样本提高比例 |
| 双跑结果可复现率 | 待测量 | 节点结果 100% 一致 | 比较两次完整测试节点与结果，skip/xfail/flaky 单独审查 |
| 基线阻断项 | 未汇总 | P0/P1=0 | 缺陷系统与基线未决项联合核对；其他项均有 owner、影响阶段与期限 |

## 6. 合规核对

| # | 核对项 | 判定 |
|---|---|---|
| C1 | fixture、日志、报告不含明文秘密、连接串或可识别客户数据 | 一票否决 |
| C2 | 未修改已应用迁移、存量配置或历史 Run；无生产执行路径重构 | 必须通过 |
| C3 | 测试未调用外部付费模型作为必过条件，skip/xfail 和 pending_env 如实记录 | 必须通过 |
| C4 | 基线绑定明确提交 SHA，后续阶段有增量复核责任人和入口条件 | 必须通过 |
| C5 | 基线测试/文档可独立 revert；若含生产缺陷修复，已拆独立提交并更新基线 | 必须通过 |

## 7. 通过标准与签字

- **通过**：A1–A6 全通过；五项业务指标达标；C1–C5 全过；无 P0/P1 遗留，Phase 1 入口清单完整。
- **有条件通过**：仅不影响 Phase 1 契约设计的 P2/P3 遗留，且每项有 owner、期限和影响边界；安全、样本兼容与双跑确定性不得有条件豁免。
- **不通过**：任一否决项、核心覆盖不足、合法样本被删除/改写、双跑不确定或 P0/P1 未关闭；整改后重验受影响项及完整基线。

输出《Phase 0 验收报告》：AC 证据、基线指标、合规核对、遗留清单、目标 SHA 和签字（架构/产品/QA/研发/安全）。
