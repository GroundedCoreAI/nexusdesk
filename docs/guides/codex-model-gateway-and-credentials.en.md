# Codex CLI: ModelGateway selection, credentials and PATH

This guide answers the operational questions raised by the P7 / Stage A
acceptance round and documents the configuration introduced by issues #165–#168.
It is written for the administrator who configures a deployment, not for the
customer who edits an Agent.

## 1. Where a valid `credential_ref` comes from

A `credential_ref` is a **UUID minted by the credential vault**. It cannot be
generated by the frontend, invented by a user, or derived from an API key. The
only way to obtain a valid one is the admin-only credential API:

```
POST /api/v1/execution-credentials
Content-Type: application/json

{
  "name": "codex-provider-key",
  "credential_type": "api_key",
  "secret": "<real provider API key>",
  "allowed_engines": ["codex"],
  "allowed_workspaces": ["<workspace id>"]
}
```

The response is `public_metadata()`; the field **`credential_ref`** is the UUID
that must be referenced. Other useful fields are `status`, `allowed_engines`,
`allowed_workspaces`, `version` and `key_version`. The plaintext secret is
write-only: no endpoint returns it.

A reference is **valid** only when all of the following hold:

| Condition | Where enforced |
| --- | --- |
| A row exists in `execution_credentials` for this tenant | publish validation + Broker |
| `status = 'active'` (not `superseded` / `revoked`) | publish validation + Broker |
| `allowed_engines` contains `codex` | publish validation + Broker |
| `allowed_workspaces` contains the Run's workspace | Broker at run time |
| The installation key at `AGENT_EXECUTION_CREDENTIAL_KEY_FILE` can decrypt it | Broker at run time |

Related admin endpoints: `GET /execution-credentials`,
`GET /execution-credentials/{credential_ref}`,
`POST /execution-credentials/{credential_ref}/rotate`,
`POST /execution-credentials/{credential_ref}/revoke`. Rotation creates a new
version but keeps the same `credential_ref`, so bound Agents do not need to
change. Revocation makes every bound Agent fail until it is rebound.

### Two ways to bind it

1. **ModelGateway lane (recommended).** Configure the reference once on the
   Gateway **connection** using the `execution_credential_ref` field of
   `POST/PATCH /api/v1/model-gateway/connections`. An Agent then only binds a
   published chat **profile**; it never carries a UUID. This is the lane that
   supports multiple providers.
2. **Legacy lane.** `AgentConfig.codex.credential_ref` holds the UUID directly.
   The Agent form offers a read-only selector populated from
   `GET /execution-credentials`; free-text UUID entry is no longer possible.
   `AGENT_CODEX_CREDENTIAL_REF` may override it at deployment level.

Publish validation resolves the whole chain and rejects an unknown, revoked, or
out-of-scope reference with `codex_credential_invalid` (HTTP 409), so a broken
version can no longer be published. A run that still hits a Broker denial is
reported as `execution_credential_unavailable` instead of the opaque
`execution_error`; the specific denial reason is recorded only in
`execution_credential_audit`.

## 2. Selecting the model and provider (Q3)

Codex is no longer tied to `deepseek-flash`. A Codex Agent binds a **ModelGateway
chat profile** through `codex.model_profile_id` +
`codex.model_profile_version`. Any connection, model and published profile in the
Gateway catalogue can be used, including custom `openai_compatible` providers.

The per-run private `CODEX_HOME/config.toml` is rendered from the resolved
route:

| TOML key | Source |
| --- | --- |
| `model` | `gateway_models.model_name` |
| `model_provider` | connection `codex_model_provider`, else a sanitized connection name |
| `base_url` | connection `codex_base_url`, else `base_url` (must be a bare https URL) |
| `wire_api` | connection `codex_wire_api` (`responses` or `chat`), default `responses` |
| `env_key` | `OPENAI_API_KEY` (a neutral variable NAME, never a value) |

The address is validated against `model_gateway_allowed_hosts`. The secret is
still injected by the Credential Broker into exactly one child environment slot;
it is never written into `config.toml`, a snapshot, a log, or an API response.

**Transport constraint.** `codex` is an external binary that requires an
OpenAI-compatible HTTP endpoint, while ModelGateway is an outbound client with
a proprietary `/model-gateway/invoke` envelope. This design therefore routes
model/provider selection, credentials and address governance through
ModelGateway; the CLI's inference traffic still goes directly to the resolved
upstream. An inbound Responses-API bridge (which would also unify retries and
audit) is a separate future phase and is not implied here.

**Compatibility.** If the profile pair is absent, the legacy lane is used:
deployment-global `AGENT_CODEX_MODEL`, `AGENT_CODEX_MODEL_PROVIDER`,
`AGENT_CODEX_MODEL_BASE_URL`, `AGENT_CODEX_CREDENTIAL_ENV_KEY` plus
`codex.credential_ref`. No published snapshot becomes unparseable.

## 3. Codex PATH (Q5)

`AGENT_CODEX_PATH_ENV` is the single effective value. It is passed from
deployment settings into the adapter and used for the child process `PATH`,
independent of any published Agent value. Changing it requires a backend
restart. The customer Agent form has no PATH field: it is a deployment detail,
not an Agent setting.

## 4. Operational checklist

1. Supply the installation key and enable the Stage-A gate flags.
2. Create the provider credential(s) with `POST /execution-credentials`.
3. Configure Gateway connections (base URL, `codex_base_url` if the provider
   needs a `/v1`-style prefix, `codex_wire_api`, `execution_credential_ref`).
4. Publish a chat profile whose model has `tool_calling` enabled.
5. In the Agent editor, select that profile under 执行与能力; optionally select a
   credential for the legacy lane. Save and publish.
6. Run a trial chat. A healthy run emits `codex.thread.started`; a credential
   problem reports `execution_credential_unavailable`, and a gate problem
   reports `adapter_disabled`.
