# 智能客服

> 这套教程记录智能客服场景的设计判断：为什么这样拆分、为什么这样约束，以及那些看起来像实现细节的取舍，如何决定产品最终长成什么样。

## 这套教程解决什么问题

智能客服很容易被做成「聊天窗口 + 一个 Agent」：界面先出现，能力后补，最后再想办法把知识、工具、工单和人工塞进去。

NexusDesk 的第一个落地场景选择了相反的顺序：先确定客户要完成的服务任务，再决定 Agent、知识、工具和人工在什么位置出现、以什么状态表达结果。

所以，这套教程不追求覆盖所有功能，而是回答三类问题：

1. **概念为什么存在**：服务应用、服务场景、业务对象、业务事实、执行能力分别解决什么问题。
2. **边界怎么划**：哪些能力属于场景，哪些属于 Agent，哪些必须在人工环节继承下来。
3. **状态怎么表达**：模拟、待确认、处理中、成功、失败、结果未知和转人工，为什么要严格区分。

接口字段、部署命令和运维细节不在这里展开，请看「使用指南」「架构」「部署与运维」。

## 写给谁

- 正在接入或配置智能客服的实施同学；
- 参与方案评审、需要判断「这个需求该放在哪一层」的产品与研发同学；
- 后续维护这套设计、需要理解原始取舍的开发者。

## 本教程的七条设计判断

这是整套教程的骨架。后续每一章，都是对其中一条判断的展开。

1. **服务应用是交付单元。** 客户最终使用的是一个服务应用，而不是一个孤立的 Agent 或页面。
2. **服务场景是核心可复用资产。** 可复用的是「客户要完成什么任务」，不是某段提示词。
3. **业务对象是一等产品组件。** 订单、设备、预订这类对象，客户和坐席都要能看见、能点选、能确认。
4. **Agent 是场景的一种执行能力，不是场景本身。** 场景决定任务与边界，Agent 只负责其中适合自动化的部分。
5. **人工工作台继承完整上下文。** 转人工交接的是场景、对象、事实、决策和轨迹，而不是一段聊天记录。
6. **行业差异用模板、配置和注册表表达。** 不用运行时的行业分支堆叠差异。
7. **状态必须严格区分。** 模拟、待确认、处理中、成功、失败、结果未知和转人工，不能共用一套模糊的「完成 / 未完成」。

## 关于写作

- 每章只回答一个问题，标题就是这个问题；
- 先写反例，再写设计判断，最后写边界条件与对应的实现位置；
- 中文与英文成对维护（`xxx.md` + `xxx.en.md`）；
- 新增页面后，在 `site/nav.mjs` 的 `scenarios` 分组登记。
